The main pieces:

challenge-container → challenge-view holds the task itself. Inside it, challenge-header contains the teal prompt bar, with the instruction text in an <h2 id="prompt-question"> ("Find the thing that can roll on a flat surface"). There's also a hidden challenge-report block (red background, "Please select an image to report") that appears only if you use the report-image feature, and an empty examples container that some challenge types fill with a sample image.

The <canvas> is the most notable element. It's 1000×940 internally, displayed at 500×470 (2x for sharp rendering on high-DPI screens), and sits on top of everything with z-index: 10. The nine images in your screenshot aren't <img> tags or separate DOM nodes at all; they're painted onto this single canvas, and clicks are interpreted by hCaptcha's script based on where they land. That's a deliberate design choice: there are no image URLs or per-tile elements in the DOM. Its aria-label points screen-reader users to the accessibility alternatives.

interface-challenge is the bottom strip: a hidden display-error alert ("Please try again"), the challenge-breadcrumbs (two dots, the first elongated, meaning round 1 of 2), and the button-submit element. It currently reads "Skip" with the aria-label "Skip Challenge, page 1 of 2"; it turns into Next/Verify once a selection is made, and contains a hidden spinner SVG for the loading state.

interface-user holds the utility controls: the language selector (that enormous list of 111 option divs is just the language dropdown, with English marked aria-selected="true", which accounts for most of the markup's size), the three-dot menu-info button for accessibility options and info, the refresh button, and the hCaptcha logo link.

challenge-modal at the end is a hidden dialog shell used for info/feedback popups, with an empty title and content until it's triggered.

A few general observations: buttons are divs with role="button" and tabindex="0" rather than native <button> elements, with ARIA attributes doing the accessibility work. And the DOM you see is only the presentation layer. The actual verification happens server-side, based on a token issued after hCaptcha evaluates the answer along with behavioural and browser signals, so nothing in this markup contains or reveals the answer.

WORKING ON FRONTEND: 

The honest caveat first: hCaptcha's client code is obfuscated and changes often, so I can't tell you its exact internals. But canvas-based UIs all work on the same well-known principle, called hit testing, and that's what's happening here.

The core idea. A canvas is just a bitmap. Once something is drawn, the browser has no idea there's a "tile" there, so there's nothing to attach a click handler to. Instead, the script keeps its own model in memory, a list of objects like "tile 4 occupies x 190-290, y 250-350", and draws the canvas from that model. When a pointer event fires on the canvas, the script takes the event's coordinates, converts them to canvas space, and checks which rectangle in its model contains that point. It then updates state (tile selected) and redraws, for example with a highlight border.

The coordinate conversion. Your canvas is 1000×940 internally but displayed at 500×470, so the script has to scale:

javascript
canvas.addEventListener('pointerdown', (e) => {
  const rect = canvas.getBoundingClientRect();
  const x = (e.clientX - rect.left) * (canvas.width / rect.width);
  const y = (e.clientY - rect.top) * (canvas.height / rect.height);

  const hit = tiles.find(t =>
    x >= t.x && x <= t.x + t.w && y >= t.y && y <= t.y + t.h
  );
  if (hit) { hit.selected = !hit.selected; redraw(); }
});

That's the generic pattern you'd use in any canvas app, such as a game, a chart library, or a drawing tool. For non-rectangular shapes, people use ctx.isPointInPath() or a hidden "colour-picking" canvas where each object is drawn in a unique colour and the pixel under the cursor identifies it.

Why a captcha vendor chooses this design. With one canvas, there are no per-image DOM nodes, image URLs, or element IDs, so the page structure reveals nothing about the challenge. The layout can also change freely (grids, drag-and-drop, click-a-point tasks) without changing the DOM, which is why the same markup serves many challenge types.
